## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ContentView gate → Core Data | onboardingComplete is read from Core Data on .task, not from in-memory state alone |
| HealthProfileView.save() → Core Data | Personal health fields written to Core Data; no network calls |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-01 | Elevation of Privilege | ContentView onboarding gate | mitigate | Gate reads `onboardingComplete` from Core Data via `UserProfileStore.fetchOrCreate` in `.task` — cannot be bypassed by in-memory state manipulation; Core Data write is required to flip the flag |
| T-5-02 | Tampering | UserProfileStore.markOnboarded | mitigate | `if profile.trialStartDate == nil` guard already implemented in UserProfileStore.markOnboarded — Phase 5 does NOT duplicate this guard; it simply calls the method from the paywall CTA (Plan 03) |
| T-5-03 | Tampering | HealthProfileView free-text inputs (allergies, conditions) | mitigate | Stored as `[String]` via NSSecureUnarchiveFromData transformable on Core Data — no SQL injection surface; no network path |

No new security surface introduced by Plan 01. The ContentView gate is a conditional
render, not an auth barrier — the iOS sandbox enforces the true security boundary.
